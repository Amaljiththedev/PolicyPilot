In one minute

If you only read one section, read this one.

An assistant that answers questions from company documents, shows its sources, refuses to guess, and always uses the latest version of a policy.

Grounded

Every answer cites the document and the passage it came from. No citation, no answer.

Honest

When the documents don't contain the answer, it says so and hands the question to a person instead of making something up.

Current

When a policy is replaced, answers come from the new version, and it can tell you what changed.

Measured

Quality is proven with numbers from an automatic test harness that runs on every code change — not with "it seems to work".

The problem

Why this is worth building.

Companies keep their rules in long documents — the staff handbook, the leave policy, the expenses policy — that almost nobody reads start to finish. So the same questions get asked again and again ("How many days of leave do I get?", "Can I expense a taxi after 9pm?"), they get answered inconsistently, and often they get answered from an old version of the document that was replaced months ago.

The real cost isn't the time spent answering. It's the decisions people make based on wrong or outdated information.

A general chatbot doesn't fix this. It has never seen your documents, and even when you give them to it, it will still produce a confident, fluent answer when the documents don't actually say anything. For an assistant like this to be trusted, two things must be true: every answer can be traced to a source, and the system is willing to say "I don't know."

What it does

The experience, from the user's side.

1 · HR adds policies

Upload a PDF, Word, HTML or text file — or, later, just drop it in a shared Google Drive folder.

2 · Staff ask questions

Through the API, or later directly in Slack: "How many days of annual leave do I get?"

3 · They get a cited answer

"25 days per year [Leave Policy v3, §2.1]." One click shows the exact paragraph.

4 · Or an honest handoff

"The policies don't cover parking. I've passed this to @HR." The question isn't lost.

Ingestion can happen weeks before anyone asks anything. Keeping the two paths separate means we can re-chunk or re-embed every document without touching the question-answering code.

The write path: getting a document in

When a document arrives, four things happen in order. If any step fails, nothing is saved — the document and all its pieces go in together or not at all.

  F[File
PDF · DOCX · HTML · TXT] --> V{Valid?

409 · 413 · 415 · 422]

  E --> T[(One transaction:
document + chunks)]
  • Parse — pull the plain text out of the file. Scanned PDFs with no text layer are rejected loudly rather than stored empty.
  • Chunk — split the text into passages, preferring to break at paragraphs, then sentences. Neighbouring chunks overlap slightly so an idea that sits on a boundary isn't cut in half.
  • Embed — turn each chunk into a list of 384 numbers that captures its meaning. Passages about similar things end up close together, so "holiday" can find "annual leave".
  • Store — save everything in PostgreSQL, with a special index (HNSW) that makes "find the closest passages" fast even with many thousands of chunks.

The read path: answering a question

The answering step is an agent: instead of searching once and hoping, the model decides what to do next, from a small set of tools, for a limited number of rounds.

sequenceDiagram
  actor User
  participant Agent
  participant Search as search_documents
  participant Doc as get_document
  participant HR as escalate_to_human
  User->>Agent: "Can I carry over unused leave?"
  Agent->>Search: leave carry-over rules
  Search-->>Agent: top passages + scores
  Agent->>Search: carry-over limit for part-time staff
  Search-->>Agent: more passages
  alt Answer is in the documents
    Agent-->>User: Answer + citations [Leave Policy v3 §4.2]
  else Nothing solid found
    Agent->>HR: hand over the question
    Agent-->>User: "The policies don't say. I've asked HR."
  end

The number of rounds is capped, so the agent can never loop forever or run up cost. Every question, answer, and the chunks used are logged for evaluation and debugging.

Supersession: always the current version

Policies change. When Leave Policy v3 replaces v2, old passages must stop appearing in answers — but they aren't deleted, because "what changed?" is a useful question too.

Slack & Google Drive NEW in v1.1

Two integrations, each chosen because it makes an existing core feature real — not to add breadth for its own sake.

The rule for integrations

An integration earns its place only if it strengthens a core feature. Drive makes supersession automatic. Slack makes escalation reach a real person. Anything else (Teams, email, Notion, indexing everyone's messages) stays out.

Google Drive — policies stay up to date by themselves

HR already keeps policies in a shared Drive folder. PolicyPilot watches that one folder. When a file is added, it's ingested. When a file is edited, the new version is ingested and the old one is marked as superseded. When a file is deleted, its chunks stop appearing in answers.

Slack — ask where you already work

Staff mention the bot in a channel or DM it. It answers in the thread with citations. When it can't find a grounded answer, it tags a named HR contact in the same thread — so escalation actually reaches a human instead of dying in a log.

Deliberately not included

Slack is an interface, not a data source. PolicyPilot does not read or index anyone's Slack messages. That would bring in personal data, noisy chat, and a permissions problem that belongs to a different product.

The golden set

A hand-written list of at least 60 questions, each with the passage that should be found and a reference answer. It's split into slices, because a single average hides where things break:

SliceExampleWhat it tests
Simple lookupHow many days of annual leave?Basic retrieval
Multi-hopCan a part-time contractor claim travel?Combining two documents
ConditionalCan I work from abroad?Answers with caveats
SupersededWhat's the leave allowance? (v2 vs v3)Using the current version
UnanswerableWhat's the parking policy?Saying "I don't know"
Adversarial SHOULDA document containing "ignore your instructions…"Injection resistance

What gets measured

Did we find the right passage?

Recall@k — was the right chunk in the top k results? MRR — how high up was it?

Is the answer supported?

Faithfulness — every claim backed by a retrieved passage. Relevancy — it actually answers the question.

Does it know when to stop?

False answer rate — how often it answers a question it should have refused. This is the headline number.

Can we trust the judge?

An LLM grades answers. We hand-label 40 items and report agreement (MCC) before trusting any judge score.

The ablation table

Each improvement (hybrid search, re-ranking, better chunking) is added one at a time, and measured against the baseline. Then each is removed from the full system. This shows exactly how much each piece contributes — and proves nothing was added just because it sounded impressive.

Non-functional requirements

  • Secrets — no secret or OAuth token in the repo, the Docker image, or any log line.
  • Failures — model, embedding, Drive or Slack failure returns a clean error, never a stack trace.
  • Cost — runs entirely on free tiers: local embeddings and re-ranker, Groq free tier for answers, Gemini free tier for the judge. Token cost per question is still recorded.
  • Tests — unit tests run without a database; integration tests run against the real stack.
  • Reproducible — one command brings the whole stack up from a clean checkout.

The ordering rule

Integrations (P10–P11) don't start until the harness has produced a baseline (P6). A fast pipeline feeding a search system nobody has measured is breadth without depth.

Out of scope

Excluded on purpose. Each would add work without adding evidence. Adding anything here requires removing something of similar size.

ExcludedWhy
Multi-tenancy / SaaSOrganisations, billing, per-customer OAuth. Proves infrastructure, not retrieval. Documented as future work instead.
Indexing Slack messages, email, personal filesA different product (personal knowledge search). Brings privacy and permission problems unrelated to policy Q&A.
Microsoft TeamsSame value as Slack, much harder to test for free.
Multi-turn chat memoryThe unit of value is one grounded answer. Memory adds a whole class of evaluation problems.
Polished web frontendSlack and the API docs are the interfaces. UI work is unbounded.
CSV / spreadsheet ingestionTables are a different retrieval problem; character chunking breaks rows.
Knowledge graphs, GraphRAG, fine-tuningSeparate specialisms. Depth in retrieval beats breadth across techniques.
Streaming responsesCosmetic at this stage.

Explaining it to other people

Ready-made answers, from a 10-second version to interview follow-ups.

The 10-second version

"It's an assistant that answers questions from company policies, shows exactly where each answer came from, and says 'I don't know' instead of guessing."

The 30-second version

"Documents are split into passages and turned into vectors so they can be searched by meaning. When someone asks a question, an agent searches, reads the best passages and either answers with citations or escalates to HR. It always uses the latest version of a policy, it syncs from Google Drive and answers in Slack — and every quality claim is backed by an evaluation harness that runs in CI."

Likely follow-up questions

Why not just use ChatGPT?
It's never seen your documents, and it will answer confidently even when they don't contain the answer. PolicyPilot is built to cite sources and to refuse, and it measures how often it wrongly answers.
How do you know it's good?
A labelled set of 60+ questions split into slices. Retrieval is scored with recall@k and MRR, answers with faithfulness, and honesty with false answer rate. Every improvement has a before-and-after number.
Why PostgreSQL instead of a vector database?
I need normal relational data anyway. Supersession is a join, hybrid search uses Postgres full-text, and one database is simpler than keeping two in sync.
What happens when a policy changes?
The Drive sync picks up the edit, ingests the new version, and marks the old one superseded. Answers switch to the new version, and can say what changed.
Why only Slack and Drive?
Each one makes a core feature real: Drive makes supersession automatic, Slack makes escalation reach a human. More connectors would add breadth, not evidence.
How would you make it multi-tenant?
Add an organisation ID to documents and chunks, enforce it in every query with Postgres row-level security, and store each organisation's OAuth tokens encrypted. Deliberately left as future work.

Glossary

RAGRetrieval-augmented generation: find relevant text first, then have the model answer using only that text.
ChunkA passage of a document (~800 characters) — the unit that gets searched and cited.
EmbeddingA list of numbers representing meaning. Similar meanings → nearby numbers.
pgvector / HNSWPostgres extension for vectors, and the index that makes nearest-neighbour search fast.
Hybrid searchCombining keyword matching with meaning-based search, so exact terms aren't missed.
Re-rankerA slower, more precise model that re-orders the top candidates.
AgentA model that chooses which tool to use next (search, read, escalate) in a bounded loop.
SupersessionA newer document version replacing an older one; the old one stops being used for answers.
Golden setHand-labelled questions with known correct passages and answers, used to score the system.
Recall@k / MRRWas the right passage in the top k? How near the top was it?
False answer rateHow often it answers when it should have said "I don't know".
AblationAdding or removing one component at a time to measure exactly what it contributes.
OAuthLetting a user grant PolicyPilot limited access to their Drive without sharing a password.
IdempotentDoing the same operation twice has the same effect as once — safe to retry.
